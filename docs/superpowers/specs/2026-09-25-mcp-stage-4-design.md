# Stage 4 — Codex MCP runtime design

Status: written spec approved for implementation planning. Scope is [MCP roadmap Stage 4](../../mcp-integrations/roadmap.md). Stage 3's execution-scoped gateway is the runtime authority. Settings UI, OAuth, catalog changes, new providers, and sandbox network changes are outside this stage.

## Outcome

An ordinary tracked Forge Agent execution can use its approved MCP tools through the existing Agent gateway. A real Codex app-server receives native MCP entries for the current invocation on both `thread/start` and `thread/resume`; a recovered execution gets fresh grants. The provider conversation identity, context iteration, workspace, and durable store remain unchanged. The runtime never receives the external MCP credential or a management/service bearer.

Stage 4 does not invent a second MCP client or transport. Codex speaks MCP to the Stage 3 gateway. The gateway remains the authority for every list/call and immediately rejects an expired, revoked, or policy-invalid grant, including a stale tool still present in provider context.

## Execution selection and ownership

The Agent application path resolves the workflow project from the trusted execution claim, then lists global connections for this installation. It selects only enabled connections whose project scope includes that project and whose approved tool set is nonempty. `ALL` and `SELECTED` are evaluated with the existing `McpProjectAccess` model. For each selected connection, the existing `McpGatewayService.issue(claim, deadline, connectionId)` rechecks the live lease and policy and issues one grant. No project ID, connection ID, or approval supplied by a model prompt is authority.

Selection produces an immutable, invocation-local snapshot containing only connection UUID, display name, stable alias, approved tool names/fingerprints, gateway path, and whether issuance succeeded. Grant tokens and external credentials never enter persisted workflow snapshots, provider turns, activity, or diagnostics. At recovery and each subsequent turn the application selects again against live policy and obtains new grants; it does not revive a prior token. Legacy executions without an `AgentSessionExecutionClaim` cannot receive grants. If they encounter an MCP-enabled project, the failure is explicit rather than silently running with missing tools; no-MCP legacy behavior stays intact.

A connection that fails independent preparation is reported with a safe, bounded diagnostic while other eligible connections remain usable. An unavailable runtime isolation boundary or an unverifiable effective tool inventory fails the MCP execution closed. Grant issuance and cleanup are idempotent; `finally` revokes all grants for the current turn on success, error, cancellation, and failed startup. Existing gateway lease/policy validation remains the safety net if cleanup itself fails.

## Native Codex configuration

Aliases are deterministic from connection UUIDs, valid for Codex MCP names, and unique across simultaneous projects and connections. Each native `mcp_servers.<alias>` entry uses the Agent loopback gateway URL, `bearer_token_env_var`, exact `enabled_tools`, and per-tool approval settings validated by the Stage 0 probe. A short developer-instruction addition explains the connection's purpose and safe name; it does not paste the full tool catalog or a credential. Tool schemas come from MCP `tools/list`.

`CodexTurnRequest` carries the safe MCP selection. A separate launch-only handle holds tokens in memory and redacts its string representation; neither a Java record's generated `toString()` nor an exception may expose them. `CodexAppServerClient` supplies the same security-relevant config, cwd, sandbox, approval policy, and runtime workspace roots to fresh and resume calls. `thread/resume` keeps the requested thread ID and fails on an identity mismatch; it never starts a substitute fresh thread. Recovery inspection remains read-only and must not issue callable grants merely to inspect a past turn. The stable Forge-managed `CODEX_HOME` retains its session store. The current audited durable-version gate (`0.154.0`) is updated only after a real installed-CLI fresh/resume/recovery fixture passes; a version mismatch continues to fail closed.

Codex config is additive across layers. A partial `mcp_servers` override cannot be treated as replace-all. The execution workspace is marked untrusted in the invocation config, which a disposable Codex 0.157.0 probe confirmed prevents its `.codex/config.toml` MCP entries from loading on fresh and resume. Before app-server startup, the launcher exposes only a root-owned, read-only Forge base config at the stable runtime `CODEX_HOME/config.toml`, masks `/etc/codex/config.toml` with a root-owned empty config, and masks the runtime home's plugin source directories in the unit mount namespace. The base config contains no MCP servers or enabled plugins. Startup fails if these masks or the base config cannot be verified. Runtime UID cannot replace the mounted config; no personal Codex home is read or changed. A post-start audit is additional verification, not the isolation mechanism.

After `thread/start` or `thread/resume`, and before `turn/start`, the client calls thread-scoped `mcpServerStatus/list` through all pages. Every callable server and every exposed tool must match the issued alias/tool set; missing or broken expected servers are surfaced as safe diagnostics and excluded from the turn. Any extra server/tool, pagination/protocol error, or unverifiable status fails closed before model execution. Inventory checks do not grant access: the gateway still authorizes every request. No-MCP turns require an empty effective MCP inventory when MCP isolation is enabled.

## Grant transfer and isolation

The existing root-owned runtime launcher remains the sole process boundary. The Agent sends a bounded, typed startup envelope containing per-alias runtime grants through the launcher's stdin before JSON-RPC begins; no token appears in argv, systemd property text, Codex config, or generated env files. The helper validates the envelope and writes a short-lived root-only credential source under its existing `/run/forge-runtime` ownership. systemd `LoadCredential` presents it to the isolated unit; a narrowly scoped runtime bootstrap places only the grant environment variables into Codex and then execs the audited Codex binary. The helper removes the source on stop/failure and never prints it. This is a transfer inside the existing helper, not a new service or generic secret framework.

`HOME` and `CODEX_HOME` remain stable across turns. The isolated runtime UID and clean environment from Stage 1 remain mandatory when MCP is enabled. The external encryption key, management/service credentials, Agent process environment, parent/sibling processes, and protected secret paths remain inaccessible. The runtime grant is distinct: its scope is one turn and approved tools, and the gateway denies it after revoke. The launcher must not expose the Agent HTTP management route by granting a service credential, nor open sandbox network as a shortcut. A loopback gateway request is the only MCP network route this design requires.

## Activity and failures

Reuse the existing `TOOL_CALL` event type. For MCP items record only a known issued alias/connection identifier, bounded tool name, status/outcome, and a small fixed safe summary such as `completed`, `tool_error`, or `failed`. Do not persist raw MCP arguments, result content, headers, token, endpoint configuration, or arbitrary exception text as `responseSummary`. Provider context may retain the real result for the agent's task; the application activity stream does not duplicate it. Unknown aliases are not accepted as valid MCP activity.

Connection startup failure is visible but does not manufacture tools or fallback credentials. Unexpected inventory, lost isolation, malformed responses, or config mismatch stop the turn with a safe error. No-mcp workflows, existing non-MCP Codex calls, and existing Stage 1 management/auth boundaries keep their behavior. Stage 3's no-retry rule for ambiguous `tools/call` remains unchanged.

## Verification and acceptance

Tests use disposable workspaces, synthetic credentials, local Agent/MCP/model fixtures, and the installed Codex protocol; personal config and production secrets are untouched. Cover `GLOBAL`/`PER_SCOPE`, concurrent projects, no-MCP and broken connections, cancel/error cleanup, disable-after-issue, stale provider tool denial, fresh → next turn → resume → recovery with a new grant and the same conversation ID, and a real read-only native Codex tool call whose upstream counter and result prove execution. Contract tests verify both start and resume config plus paginated inventory before turn. A sentinel home/project/plugin MCP must never be callable; canaries must be absent from process args, config snapshots, activity, logs, and public errors. Disposable OS probes check protected paths, environment and parent/sibling visibility; only actually run probes are marked PASS.

Run focused Codex/runtime/gateway tests, full Agent and Nexus verify, the existing engineering E2E without MCP, `git diff --check`, and affected dependency analysis. Record exact commands, results, skips and `NOT_VERIFIED` items in `docs/mcp-integrations/stage-4-evidence.md`. Production provisioning, live external providers, deployment TLS, and sandbox-network policy are not implied by local fixture success.

# Stage 4 Codex MCP Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Approved global MCP connections become native Codex tools for a tracked Forge Agent execution, including durable resume, while the existing gateway alone holds external credentials and authorizes calls.

**Architecture:** The Agent application layer selects connections and issues execution-scoped grants. Codex infrastructure maps the safe selection to native app-server config and verifies the effective inventory before a turn. The existing isolated systemd launcher transfers short-lived grants through a credential file, preserves the durable home, and blocks other config layers before startup.

**Tech Stack:** Java 21, Spring Boot 3.3.4, Jackson JSON-RPC, existing Codex app-server client, Python 3 root-owned runtime helper, systemd 259 in disposable OS probes, Maven/JUnit/ForgeIT. No new HTTP or MCP framework.

**Spec:** [2026-09-25-mcp-stage-4-design.md](../specs/2026-09-25-mcp-stage-4-design.md); [roadmap.md](../../mcp-integrations/roadmap.md) Stage 4.

## Global Constraints

- Work in the regular `feature/SITIONIX-151` branch; do not create a worktree or modify personal Codex/Maven config, production secrets, deployment, or sandbox network policy.
- No external credential, service/operator bearer, or runtime grant token in provider config, argv, activity, exception text, logs, or persisted snapshot.
- Preserve Stage 3 gateway authorization, admission, no-retry and lifecycle behavior; use the existing `McpGatewayService.issue` and `revokeExecution` APIs.
- Stable `CODEX_HOME` and thread identity; no fallback to a fresh thread after resume failure. Update the `0.154.0` durable/recovery pin only after an actual installed-version fixture proves the new version.
- Use the current Forge Agent hexagonal modules, typed Spring boundaries, and `TOOL_CALL` event; no generic security or transport framework.
- Real fixtures use synthetic credentials and local read-only MCP. Mark OS isolation, live provider, or deployment checks `NOT_VERIFIED` unless actually run.

## Review Focus

- A legacy untracked execution in an MCP-enabled project must fail visibly rather than silently skip a usable connection (Task 1 test).
- Two projects using the same global connection must receive distinct turn tokens, while `SELECTED` excludes a foreign project (Task 1 test).
- A malformed or oversized startup envelope must fail before systemd starts and must not echo a token in stderr (Task 2 test).
- A status page that adds an unexpected server on its second cursor page must stop before `turn/start` (Task 4 test).
- A free-form MCP result or failure containing a synthetic canary must not enter `TOOL_CALL`, worker logs, or exception text (Task 5 test).

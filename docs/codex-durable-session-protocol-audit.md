# Codex Durable Session and Resume Protocol Audit

Date: 2026-09-04  
Scope: Forge Agent Codex app-server adapter only. No Forge session persistence, Node schema, UI, or production resume behavior is introduced by this audit.

## Verdict

Codex CLI `0.153.2` supports durable threads and successfully resumes them after the original app-server process exits. A real two-process smoke test preserved conversation continuity. Phase 1 may safely begin if Forge treats the protocol as version-pinned, persists identities before dependent operations, serializes writers per thread, and never replaces a failed resume with a new thread.

One blocker exists outside the durable-thread mechanism: although the generated stable schema contains `turn/completed`, neither live turn emitted it. Both emitted a final `item/completed`, `thread/tokenUsage/updated`, and `thread/status/changed` with `status.type=idle`. The current Forge adapter waits only for `turn/completed`; Phase 1 must explicitly resolve and test this `0.153.2` completion behavior instead of assuming the schema event is delivered.

## Confirmed session APIs

All methods below are present in the non-experimental schema bundle generated by `0.153.2`.

| Method | Confirmed behavior |
| --- | --- |
| `thread/start` | Starts a thread. `ephemeral=false` creates a persisted rollout under Codex home. Omitting/null `ephemeral` is permitted by schema, but Forge should send `false` explicitly. |
| `thread/resume` | Requires `threadId`; all other fields are optional overrides. `{threadId}` alone resumed successfully in a fresh PID. |
| `turn/start` | Requires `threadId` and `input`; response contains `turn.id`. |
| `thread/read` | Requires `threadId`; metadata-only (`includeTurns=false` or omitted) succeeds. `includeTurns=true` emitted a deprecation notice and did not return during the audit window. |
| `thread/list` | Supported with optional pagination/filter fields; returned the durable smoke thread. |
| `thread/turns/list`, `thread/items/list` | Supported and recommended by server deprecation notices instead of full-history hydration. Not exercised beyond schema confirmation. |
| `turn/interrupt` | Requires both `threadId` and `turnId`. Existing Forge already emits this shape on timeout/policy failure. |
| `thread/compact/start` | Requires `threadId`. Schema-confirmed; not destructively exercised in the smoke thread. |

The resume schema also describes history- and path-based forms, with precedence `history > non-empty path > threadId` for non-running threads. Those fields are not exposed in the generated v2 `ThreadResumeParams` used here and are unnecessary for Forge Phase 1. Forge should use `threadId` only.

## Exact Phase 1 JSON-RPC contract

Every request is a newline-delimited JSON object with a client-selected JSON-RPC correlation `id`. The current transport accepts string IDs. Notifications have `method` and `params` but no `id`.

Initialize each fresh process before session calls:

```json
{"id":"1","method":"initialize","params":{"clientInfo":{"name":"forge_agent","title":"Forge Agent","version":"0.0.1"},"capabilities":{"experimentalApi":true,"requestAttestation":false}}}
{"method":"initialized","params":{}}
```

### Durable start

Forge should preserve its existing policy fields but change only `ephemeral` for the durable path:

```json
{
  "id": "2",
  "method": "thread/start",
  "params": {
    "model": "gpt-5.6-sol",
    "developerInstructions": "...",
    "approvalPolicy": "never",
    "sandbox": "workspace-write",
    "cwd": "/absolute/execution/workspace",
    "runtimeWorkspaceRoots": ["/absolute/execution/workspace"],
    "ephemeral": false,
    "config": {
      "web_search": "disabled",
      "features": {"shell_tool": true},
      "agents": {"enabled": false}
    }
  }
}
```

The generated request schema explicitly includes `model`, `modelProvider`, `cwd`, `developerInstructions`, `baseInstructions`, `approvalPolicy`, `sandbox`, `serviceName`, `serviceTier`, `personality`, `config`, and `ephemeral`, all optional. The live response contains more compatibility fields than the generated response schema:

```json
{
  "id": "2",
  "result": {
    "thread": {
      "id": "01a06b5c-8ed3-7fa3-8b07-edb7b3836a92",
      "ephemeral": false,
      "status": {"type": "idle"},
      "path": "/home/vlad/.codex/sessions/2026/09/04/rollout-...jsonl",
      "cwd": "/tmp/forge-ai-SITIONIX-110",
      "cliVersion": "0.153.2",
      "turns": []
    },
    "model": "gpt-5.6-sol",
    "modelProvider": "openai",
    "cwd": "/tmp/forge-ai-SITIONIX-110",
    "approvalPolicy": "never",
    "sandbox": {"type": "readOnly", "networkAccess": false}
  }
}
```

Persist `result.thread.id` immediately after validating that it is a nonblank string. Do not wait for `thread/started` or the first turn.

### Resume

The minimal and recommended request is:

```json
{"id":"2","method":"thread/resume","params":{"threadId":"01a06b5c-8ed3-7fa3-8b07-edb7b3836a92","excludeTurns":true}}
```

The smoke test proved `{ "threadId": "..." }` alone is sufficient and restores the persisted model, provider, cwd, instructions/config-derived behavior, and conversation history. `excludeTurns:true` is recommended because live resume without it emitted:

```json
{"method":"deprecationNotice","params":{"summary":"Full-history hydration is deprecated for paginated threads; use `excludeTurns: true`, then page with `thread/turns/list` and `thread/items/list`.","details":null}}
```

Model, provider, cwd, developer/base instructions, approval policy, sandbox, personality, service tier, and config may be sent as overrides but are not required to locate or resume the thread. Phase 1 should omit overrides unless Forge has an explicit, validated policy for changing them. Validate that `resume.result.thread.id` exactly equals the requested persisted ID.

Unknown thread behavior was exercised:

```json
{"id":"4","method":"thread/resume","params":{"threadId":"01a00000-0000-7000-8000-000000000000"}}
{"id":"4","error":{"code":-32600,"message":"no rollout found for thread id 01a00000-0000-7000-8000-000000000000"}}
```

This is a terminal resume failure for that provider operation. Forge must expose/record the failure and must not issue `thread/start` automatically.

### Turn start and identity

```json
{
  "id": "3",
  "method": "turn/start",
  "params": {
    "threadId": "01a06b5c-8ed3-7fa3-8b07-edb7b3836a92",
    "input": [{"type":"text","text":"Continue.","text_elements":[]}],
    "model": "gpt-5.6-sol",
    "effort": "high",
    "outputSchema": {}
  }
}
```

Only `threadId` and `input` are schema-required. Model, effort, cwd, approval policy, sandbox policy, service tier, summary, and personality are optional overrides that affect this and subsequent turns. Forge's existing request intentionally supplies model/effort/output schema.

```json
{"id":"3","result":{"turn":{"id":"01a06b5c-9e27-71d2-b588-bc758608b84c","items":[],"status":"inProgress","error":null}}}
```

Persist `result.turn.id` immediately after validating it, before interrupt, retry, status correlation, or other turn-scoped operations. Treat both thread and turn IDs as opaque nonblank strings; their observed UUIDv7-like format is not a contract.

### Interrupt

```json
{"id":"4","method":"turn/interrupt","params":{"threadId":"...","turnId":"..."}}
```

Both identities are required. An interrupt must target the exact active pair; never infer a turn from “latest”.

## Observability event inventory

These are in the stable generated schema unless noted otherwise.

| Concern | Events/items and important fields |
| --- | --- |
| Plan | `turn/plan/updated {threadId, turnId, plan[], explanation?}`. `item/started`/`item/completed` can carry item type `plan`; its content is explicitly described as experimental and completed content is authoritative. |
| Reasoning summary | Item type `reasoning` has `summary[]` and `content[]`; deltas: `item/reasoning/summaryTextDelta`, `summaryPartAdded`, `textDelta`. Do not expose private reasoning beyond fields actually supplied. |
| Command execution | Item type `commandExecution` plus `item/commandExecution/outputDelta` and `terminalInteraction`; completed item includes command, cwd, status, aggregated output, exit code, duration, and command actions. |
| File changes | Item type `fileChange`; `item/fileChange/outputDelta` and `patchUpdated`; approval request is `item/fileChange/requestApproval`. |
| Tool/MCP | Item type `mcpToolCall` and `item/mcpToolCall/progress`; dynamic tool calls and MCP server status events also exist. |
| Warnings/errors | `warning` (message, optional threadId), `configWarning`, `deprecationNotice`, `error`, guardian and model verification/reroute notifications. |
| Token usage | `thread/tokenUsage/updated {threadId, turnId, tokenUsage}` with `total`, `last`, and `modelContextWindow`; counts include total/input/cached/cache-write/output/reasoning-output tokens. |
| Compaction | Preferred item type `contextCompaction`. Legacy `thread/compacted {threadId, turnId}` is schema-deprecated. Manual request: `thread/compact/start {threadId}`. |
| Lifecycle | `thread/started`, `thread/status/changed`, `turn/started`, schema-declared `turn/completed`, `item/started`, `item/completed`. Live `0.153.2` completion caveat is described above. |

All turn-scoped events must be correlated by the pair `(threadId, turnId)`, and item events additionally by `item.id`/`itemId`. Notifications with malformed or missing required identity must fail explicitly rather than being attached to a guessed current execution.

## Current Forge adapter gap analysis

Current production flow is:

```text
start a workspace-bound app-server process
→ initialize (experimentalApi=true)
→ thread/start with ephemeral=true
→ extract result.thread.id
→ turn/start
→ extract result.turn.id
→ wait for item/completed + turn/completed
→ close process
```

Required later Phase 1 changes:

1. Add an explicit “new durable session” operation that sends the existing thread parameters with `ephemeral=false` and persists validated `thread.id` before accepting a turn.
2. Add an explicit “resume existing session” operation that starts/initializes a fresh process and sends `thread/resume {threadId, excludeTurns:true}`. Never call `thread/start` in its error branch.
3. Persist validated `turn.id` as soon as `turn/start` responds, before waiting for events or allowing interrupt.
4. Route all notifications using provider IDs, not Forge-local process/session IDs.
5. Expand observability parsing. Today Forge handles only `item/started`, `item/completed`, `turn/completed`, and approval server requests. It ignores plan updates, reasoning deltas, token usage, warnings, compaction and most lifecycle events.
6. Change the current generation policy before treating MCP calls as observable: it currently fails and interrupts a turn on item type `mcpToolCall`, although `0.153.2` declares it as a normal structured item.
7. Resolve live completion semantics for `0.153.2`. A safe candidate is to finalize only after a final-answer `item/completed` and the same thread reaches idle, while separately recording a schema `turn/completed` if emitted. This must be contract-tested before production use.
8. Keep existing ephemeral `execute()` untouched until storage ownership, restart recovery, and single-writer enforcement exist.

The audit adds a package-private protocol helper and parser for tests/future integration, but neither is wired into `CodexAppServerClient.execute()`.

## Persistence ordering and recovery rules

Recommended Phase 1 state machine:

```text
INITIALIZING
  durable start response → validate thread.id → persist threadId → READY
  resume response        → validate exact matching thread.id → READY
  resume error/mismatch  → FAILED (no fallback)

READY
  turn/start response → validate turn.id → persist turnId + running status → RUNNING

RUNNING
  structured events → correlate exact threadId/turnId
  completion/failure → persist terminal state and last usage → READY or FAILED
```

The thread ID must be durable before the first `turn/start`. The turn ID must be durable before subsequent provider operations, especially `turn/interrupt`. If persistence fails, do not continue the provider operation because Forge would lose its correlation/recovery handle.

## Concurrency and ownership

- Schema text says resuming a thread that is already running in the same app-server rejoins it. A non-empty path then acts as a consistency check.
- The schema does not promise safe concurrent mutation by independent app-server processes, and this audit did not intentionally race two writers against one rollout.
- Forge must therefore enforce one logical writer/active turn per `threadId` across workers and processes. Use a database lease/lock with fencing or an equivalent single-owner mechanism before resume/turn/interrupt.
- Do not start two turns concurrently for one thread. `turn/start` may steer an active turn in some conditions, and the schema defines errors when an active turn cannot accept same-turn steering. Forge Phase 1 should not depend on steering.
- Reads/listing may be performed separately, but metadata can be eventually updated while a writer is active; treat notifications from the owning process as authoritative for the active operation.

## Unsupported or uncertain features

- Safe multi-process concurrent writers for one thread: unsupported by this Forge contract and not guaranteed by schema.
- Automatic fallback from resume to new thread: explicitly unsupported.
- Resume by raw history or rollout path: schema prose mentions it, but Phase 1 does not need it and generated v2 params expose only thread ID plus overrides.
- Full-history hydration through resume or `thread/read(includeTurns=true)`: deprecated and observed to stall; use paginated turn/item APIs.
- Guaranteed delivery of `turn/completed` in `0.153.2`: contradicted by both live turns despite presence in stable schema.
- Manual compaction outcome and automatic compaction thresholds: schema-confirmed but not forced in the smoke test; treat `contextCompaction` items as the forward-compatible event.
- Plan item streaming content: explicitly experimental even though related method/item definitions appear in the stable bundle.
- Cross-version compatibility: not established. Forge should record Codex version with the session and gate durable operations to tested versions or rerun this contract suite on upgrade.

## Phase 1 recommendation

Phase 1 is safe to start for durable identity persistence and explicit start/resume orchestration. It is not safe to ship production durable execution until completion detection, single-writer ownership, persistence ordering, and the current MCP policy are implemented and tested. Pin/support `0.153.2` explicitly, retain unknown fields, reject malformed/mismatched identities, and make failed resume terminal rather than silently creating a new conversation.

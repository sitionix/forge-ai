# MCP Integrations — прості flows

Це порядок дій користувача. Один MCP connection зберігається в Agent. Nexus передає typed management запити між Console та Agent. Підключення з каталогу й Custom MCP проходять один і той самий шлях збереження та перевірки.

## 1. Показати доступні MCP

**Вхід:** користувач відкриває Settings → Integrations → Catalog.

**Дія:** Agent читає одну сторінку офіційного MCP Registry через REST API і коротко кешує її. Forge повертає назву, опис, версію, remote HTTP URL і курсор наступної сторінки. Registry не гарантує відомостей про спосіб авторизації, тому їх з’ясовує користувач під час підключення. Картка не містить credentials і сама нічого не підключає.

**Результат:** користувач обирає картку або переходить до Custom MCP. Каталог не є джерелом істини для вже створених connections.

**Roadmap:** це перший окремий backend flow каталогу з 5-хвилинним in-memory кешем сторінок. UI карток, рекомендації та синхронізований durable cache залишаються в пізніших етапах roadmap.

## 2. Створити Custom MCP

**Вхід:** назва, URL, спосіб авторизації та потрібний секрет.

**Дія:** Console передає typed запит через Nexus; Agent зберігає connection і секрет у чинному захищеному сховищі. Користувач запускає перевірку: Agent підключається до MCP, отримує tools і повертає зрозумілий результат. Користувач обирає проєкти й дозволені tools та вмикає connection.

**Результат:** connection з’являється у Connected. Невдала перевірка не видається за успішне підключення і не відкриває доступ агенту.

**Roadmap:** модель і management API — Stage 1; перевірка й tools — Stage 2; UI та робота агента — Stages 3–5.

## 3. Підключити MCP з каталогу

**Вхід:** вибрана картка і заповнені користувачем поля, яких бракує: наприклад, instance URL або credential.

**Дія:** картка підставляє відомі поля в той самий flow, що й Custom MCP. Далі виконуються ті самі збереження, перевірка, вибір проєктів і tools.

**Результат:** звичайний connection у Connected. Окремого connection engine чи provider-specific executor немає. Оновлення картки не переписує збережений URL або credential.

**Roadmap:** Stage 8 поверх готового Custom flow.

## 4. Показати підключені MCP

**Вхід:** користувач відкриває Settings → Integrations → Connected.

**Дія:** Forge читає з Agent connections поточної інсталяції та повертає назву, host, стан, останню перевірку й налаштований доступ. Секрети не повертаються.

**Результат:** список і деталі реально збережених connections, незалежно від доступності каталогу.

**Roadmap:** читання даних — Stage 1; сторінка Console — Stage 5.

## 5. Керувати connection

**Вхід:** користувач відкриває connection і обирає Test, Edit, Enable/Disable або Remove.

**Дія:** Forge виконує одну обрану дію і повертає фактичний стан. Test оновлює inventory, але сам не вмикає connection і не дозволяє нові tools. Disable і Remove припиняють подальший доступ агента; Remove також видаляє локальний credential.

**Результат:** Connected показує стан із backend. Помилка дії не замінюється оптимістичним успіхом у UI.

**Roadmap:** базове керування — Stage 1; Test — Stage 2; runtime відкликання — Stage 3; UI — Stage 5.

## 6. Використати дозволений tool в агенті

**Вхід:** користувач запускає звичайне агентське виконання у проєкті, якому дозволено connection і конкретний tool.

**Дія:** Forge передає Codex доступ лише до дозволеного MCP на час цього виконання. Виклик проходить через Agent; зовнішній credential залишається у Forge. Той самий порядок працює для fresh, resume і recovery.

**Результат:** агент бачить і викликає справжній MCP tool; після Disable/Remove нові виклики відхиляються.

**Roadmap:** gateway — Stage 3; Codex runtime — Stage 4; end-to-end UI перевірка — Stage 5.

## Найближча робота

Stage 1 уже дає збереження й management API. Flow 1 «доступні MCP» реалізовано окремо: він лише читає Registry і не змінює connections. Наступний backend зріз Flow 2 — Test connection, inventory та явне підтвердження tools; UI й runtime виконуються у відповідних наступних stages.

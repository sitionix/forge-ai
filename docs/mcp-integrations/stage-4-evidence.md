## Verified behavior

- **PASS — selection and scope:** application tests cover `ALL`, `SELECTED`, disabled and empty-tool connections, two projects, independent connection failure, untracked legacy rejection, distinct grants, and revocation. The executor passes only the safe selection into Codex JSON-RPC and the alias-to-token handle into the isolated launch path.
- **PASS — native config and inventory:** focused tests cover fresh/resume equality of MCP config and security fields, exact tool names and env reference, no token in provider config, empty inventory for a no-MCP selection, broken/missing expected tools with fixed diagnostics, unexpected alias/tool on a second page, repeated cursor, malformed page and deadline failure. The unexpected inventory case emits zero `turn/start` requests. A mismatch between selection and grant aliases fails before process launch.
- **PASS — local real Codex fixture:** `python3 scripts/runtime/tests/stage4_codex_fixture.py` on installed `codex-cli 0.157.0` reports `STAGE4_NATIVE_ASSERTION PASS`. It executes two native read-only `tools/call` operations across fresh/resume with the same thread ID and different synthetic grants, rejects the first grant after revocation in the fixture, performs read-only recovery with no grant, and never calls a project-config sentinel. This is a disposable local fixture, not a production deployment.
- **PASS — joined HTTP fixture:** opt-in `McpCodexRuntimeEndToEndHttpTest` reports 1 test, 0 failures/errors/skips. Real Codex makes fresh and resumed native tool calls through `McpGatewayController`, `McpGatewayRuntimeFilter` and `McpGatewayProtocolAdapter` at the actual Spring HTTP port. Both synthetic grants reach the runtime policy mock with the approved tool and arguments. No external provider or production credential is used.
- **PASS — secret-safe activity/errors:** canary tests cover MCP result, arbitrary status/error, unknown alias, failed selection and worker failure persistence. MCP-specific worker logging uses fixed text without the exception graph; no canary appears in the observed test output or persisted event payload. Ordinary dynamic-tool mapping remains covered by existing tests.
- **PASS — runtime helper unit and user-systemd credential probe:** 17 Python launcher tests and 4 focused Java launch/boundary tests pass. A disposable user-systemd probe confirmed that `LoadCredential` reaches the bootstrap, which passes only fixed grant env names and stable home into Codex. The source is mode `0600` and removed on stop/failure in unit tests.

## Environment limits and deployment prerequisites

- **NOT_VERIFIED — root-systemd mount isolation:** the disposable user-systemd manager proved credential loading and clean bootstrap env, but it did not prove root-owned transient-unit `BindReadOnlyPaths` or `InaccessiblePaths`. A user-manager mount probe returned 226 for the bind and did not mask the sentinel. That result does not establish behavior for the production system manager. Stage 4 deployment requires a privileged disposable acceptance run that confirms the mounted clean `CODEX_HOME/config.toml`, empty `/etc/codex/config.toml`, masked plugin sources and denied access to protected paths. No production provisioning or sandbox-network change was made.
- **Prerequisite — root-owned config:** deploy root-owned regular `codex_config` and empty `empty_system_config` files, create non-symlink mount targets in the stable runtime home with safe permissions, and update the root-owned launcher JSON to include those two source paths. The helper fails closed without them. Both files must contain no MCP/plugin configuration.
- **NOT_VERIFIED — full management-persisted connection to isolated production execution:** the joined fixture verifies the actual Spring gateway HTTP route and Codex native call with a mocked gateway policy port; Stage 1 persistence and Stage 3 live policy have separate green tests. A single deployed run through management creation, root-systemd launch and real workflow execution has not been exercised.
- **NOT_VERIFIED — live external MCP provider, production TLS/private CA, production deployment, independent privileged sandbox/secret inspection and the historical live-model engineering E2E.** No personal Codex config, Maven config or production secret was modified. No sandbox network was opened.
